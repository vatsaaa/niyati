# Niyati — Business Specification

Last updated: 2025-12-17

Purpose
-------
This document captures the business rules, product definitions, monetization model, user journeys, KPIs, and operational policies for Niyati. It is intended for product managers, business stakeholders, and engineers implementing features tied to product decisions.

1. Product summary
------------------
- Niyati is a conversational astrology assistant that delivers personalized horoscopes, birth-chart insights, and guidance. Interaction is chat-based (UI) and personalized messages are generated by an LLM via n8n workflows.
- Core product pillars: simple onboarding, lightweight personalization, configurable credit-based monetization, and quality feedback loops.

2. Target users and segments
----------------------------
- Casual (Free) Users: Discover daily horoscopes and ask occasional questions. They receive a monthly free credit allowance (default 10 credits/month).
- Engaged (Paid) Users: Pay to top up credits to access premium, detailed analyses (career, love, health, predictions). Paid credits are granted per INR paid.
- Power Users / Analysts: Use frequent, in-depth queries and may be offered subscription bundles or enterprise access.

3. Core value propositions
-------------------------
- Fast, friendly onboarding — phone-only login with minimal friction.
- Personalized greetings and context-aware replies (e.g., location-aware greetings, prior-session context through RAG).
- Clear, predictable monetization: credits model with configurable pricing and transparent QR-based top-ups.
- Feedback-driven quality improvements via thumbs up/down that feed training and prompt tuning.

4. Monetization & Pricing model
--------------------------------
Primary model: prepaid credits. Business parameters are configurable via `app_config`.

- Free monthly allowance: `credits_monthly_free` (default 10 credits/month). Reset on the 1st of each month.
- Credit costs:
  - `credits_horoscope_cost` (default 2 credits) — short daily horoscope queries.
  - `credits_premium_cost` (default 4 credits) — in-depth, future-facing, or multi-part questions.
- Payment mechanics:
  - Customer scans a QR that corresponds to a fixed `payment_amount_inr` (default ₹500).
  - After payment, user shares `UPI ID` and `12-digit UPI txn id` in chat.
  - Worker or admin verifies payment; backend `POST /users/add-credits` converts INR to credits at `credits_per_10_inr` (default 1 credit per ₹10) and increments `credits` and `total_paid_amount`.

Example: ₹500 at 1 credit/₹10 = 50 credits.

5. Deduction & accounting rules
--------------------------------
- Deduction occurs only after a successful bot answer is delivered to the user.
- The client calls `POST /users/deduct-credits` with `{ phoneNumber, amount }` and the server atomically updates `credits = GREATEST(credits - amount, 0)` and returns the updated balance.
- The UI updates the displayed credits from the server response. If the deduction fails for any reason, the UI should show a warning and not assume credits were consumed.
- If a user has insufficient credits for a premium query, the UI should block the request and surface payment options.

6. Free vs Paid feature gating
------------------------------
- Free users (zero payment history) are limited to daily horoscope queries and must have sufficient credits to proceed.
- Paid users (total_paid_amount > 0) can access premium queries until credits deplete.

7. Rate limiting & abuse prevention
----------------------------------
- Rate limits (per phone number):
  - Free users: 5 queries per rolling 24-hour period (configurable).
  - Paid users: 50 queries per rolling 24-hour period (configurable).
- Enforcement: middleware on webhook/call endpoints and request counters stored in a fast datastore (Redis preferred). For minimal setup, store counters in Postgres with TTL cleanup jobs.
- Security: throttle repeated webhook calls and detect anomalous patterns (rapid-fire queries, many unique messages from same phone) and temporarily block or require CAPTCHA.

8. User journeys (detailed)
--------------------------

New user onboarding
- 1) User opens app, consents to privacy.
- 2) Enters phone number and submits.
- 3) Client calls `POST /users/identify` → backend returns `returning: false`.
- 4) Client prompts for details (name, DOB, TOB, POB). User provides in chat or via form.
- 5) Client calls `POST /users/profile` to persist profile; backend sets `credits` to `credits_monthly_free` and `credits_last_reset` now.
- 6) Client displays `Credits: X` in header.

Returning user
- 1) User logs in with phone.
- 2) Client calls `POST /users/identify` → backend returns user object (including `credits`, `last_login_location`, `total_paid_amount`) and `config`.
- 3) Client fetches current browser location and compares to `last_login_location`; if different send `locationChanged` system prompt to n8n to generate a location-aware greeting.
- 4) Client persists the new `last_login_location` via `POST /users/profile` immediately so the next login compares against it.
- 5) `Credits: N` is shown in header and is kept in sync after each deduction.

Chat flow with credits
- 1) User composes message.
- 2) Client computes `queryCost` using `niyati_credits_config` (localStorage) and validates `userCredits >= queryCost`.
- 3) If OK, client calls n8n; when a successful reply is received, client calls `POST /users/deduct-credits` with the exact `amount` consumed.
- 4) Server returns new `credits`; client updates UI. If credits <= `credits_low_threshold`, show payment QR once per session.

9. Feedback & quality loop
-------------------------
- Each bot message includes a message id (client-generated timestamp/uuid).
- User can thumbs up or down. On tap, client calls `POST /api/v1/feedback`.
- Feedback is stored in `message_feedback` and is available for:
  - Prompt tuning (adjusting system prompts for n8n)
  - RAG retriever weighting (prioritize high-signal conversations)
  - Product metrics (feedback ratio per topic, per intent, etc.)

10. Key Performance Indicators (KPIs)
----------------------------------
- Activation & Onboarding
  - New signups per day (by phone)
  - % of new users who complete profile within 7 days
- Engagement
  - Daily active users (DAU)
  - Average queries per user per day
  - Retention (D1, D7, D30)
- Monetization
  - Paid conversions per day
  - Average revenue per paying user (ARPPU)
  - Credits consumed per day
- Quality
  - Feedback ratio (thumbs up / total feedback)
  - NPS survey (optional)

11. SLAs & availability targets
------------------------------
- API uptime: target 99.9% for production endpoints.
- n8n/LLM dependency: best-effort; have a fallback webhook configured and graceful fallback messages.
- Critical path: credit deduction and profile upsert must be atomic and reliable — monitor DB errors and webhook failures.

12. Fraud, refunds, and dispute handling
--------------------------------------
- Payment verification: an operator or an automated worker should verify UPI transactions (matching UPI txn id and amount) before crediting the user's account.
- Refund policy: define business rules (e.g., no refunds for digital goods unless fraudulent) and implement an admin flow for manual refunds where needed. Record `refunds` table entries for audit.

13. Localization & languages
---------------------------
- Support multiple languages starting with Hindi: UI strings, prompts, n8n system messages and fallback content must be translatable.
- Keep input and output encoding in UTF-8 and ensure LLM prompts request the target language when generating responses.

14. Legal & privacy considerations
---------------------------------
- Ensure `consent_given` is captured prior to storing PII or sending it to external services.
- Store minimal PII (phone only) and redact logs where possible. Use secure secrets management for DB creds and third-party keys.

15. Analytics & instrumentation
------------------------------
- Events to capture (minimal list): `user.identify`, `profile.saved`, `webhook.sent`, `webhook.response`, `credits.deducted`, `credits.added`, `feedback.submitted`, `payment.submitted`.
- Push logs and metrics to a centralized system (e.g., Prometheus + Grafana, or cloud-managed analytics) and create dashboards for KPIs above.

16. Product roadmap (near-term priorities)
-----------------------------------------
1. Implement feedback recording (`message_feedback`) and UI controls.
2. Add rate-limiting by phone with dynamic thresholds.
3. Add payment verification worker and an admin UI to reconcile manual payments and credit additions.
4. Integrate RAG to retain prior user context for personalized responses.
5. Add analytics dashboards and export pipelines for ML training.

Appendix: sample pricing & conversion
-----------------------------------
- Example configuration (defaults):
  - `credits_monthly_free` = 10
  - `credits_horoscope_cost` = 2
  - `credits_premium_cost` = 4
  - `payment_amount_inr` = 500
  - `credits_per_10_inr` = 1

Conversion example:
- User pays ₹500 → credits awarded = floor(500 / 10) * credits_per_10_inr = 50 credits.

End of business spec
